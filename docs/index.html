What changed before it broke?

changefeed puts every production change on one timeline: deploys, Argo CD syncs, ConfigMap edits, Helm releases, Terraform applies, AWS console changes and feature flags. When an alert fires, it ranks the changes most likely to have caused it, and shows why.

The first ten minutes of an incident

Most outages start with a change. Finding that change is still manual work.

"Did anyone deploy?"

The answer is spread across tools

Deploys are in GitHub, syncs are in Argo CD, Terraform runs are in CI logs, console clicks are in CloudTrail, and flag changes are in another SaaS. Someone has to check each one while the alert keeps firing.

"It was only a config change"

Some changes skip the pipeline

A kubectl edit on a ConfigMap, a flag ramp or an RDS parameter change never shows up as a deploy. These are the changes people forget to mention.

"Which of these 40 changes?"

A list is not an answer

changefeed links each PR to its pipeline run, Argo CD sync and rollout. It then scores each change set against the alerting service and its dependencies.

How it works

Collect, normalize, correlate, answer.

Collectors only read. Every event is converted to one CloudEvents-compatible schema, redacted, and linked to the other events from the same change before it is stored.

Sources

Feature flags, runbooks CLI · CloudEvents API

changefeed server

1
Collect

Kubernetes is watched in-cluster with get/list/watch. Everything else pushes, with retries and deduplication by event ID.

2
Normalize

Every change becomes a ChangeEvent: who, what, where, when, kind, risk, revision and links.

3
Redact

Sensitive keys and Secret-sourced env vars are masked. Tokens, keys, JWTs and URL credentials in diffs are removed before storage.

4
Correlate

Events are grouped into change sets by PR number and commit SHA. A full SHA, an Argo CD revision and a short image tag all match.

5
Rank

Change sets are scored against an incident by service, dependencies, time gap, risk and whether they skipped CI. Every point has a reason.

storage: SQLite (WAL) on one volume · retention 30 days

Integrate

Start with the cluster, then add sources one at a time.

Each source works on its own, so you can start with Kubernetes alone and add GitHub, Argo CD and CloudTrail later. Every write credential is limited to its own lane.

API and Prometheus

Every view is a JSON endpoint. Deploy frequency per service falls out of the ingest counter.

GET /api/v1/events?since=1h&env=prod&service=cart
GET /api/v1/suspects?service=checkout-api&at=14:32
# deploys per day, by service
sum by (env) (increase(changefeed_events_ingested_total{kind="deploy"}[1d]))

Secure by default

The questions your security team will ask, answered up front.

Read-only access

The cluster role grants only get, list and watch, or a namespaced Role if you list namespaces. AWS pushes through EventBridge, so changefeed holds no cloud credentials.

No secret values

Sensitive-looking keys are masked. Env vars from Secrets are shown by reference, never resolved. Helm release Secrets are read for their labels only.

No static CI secrets

GitHub Actions sign in with OIDC, checked against allowed repositories and environments. The actor and repository come from the signed token, not the request body.

Scoped tokens

Other senders use tokens stored as SHA-256 hashes. Each token is read-only or write-only, can write only its own lane, and has a rate limit.

Hardened image

Distroless, non-root, read-only root filesystem. Signed with cosign keyless, with an SBOM and SLSA provenance on every release.

Built to run in production

Health and readiness probes, Prometheus metrics, JSON logs, retention purge, a values schema and a helm test. One pod, one volume.
